# 升级追踪与轮询

这份文档解决一个问题：开源模型会被创作者持续迭代，如何及时发现更新、判断要不要升级，并在升级出问题时安全回滚——同时把"检测到更新只报告、不自动升级"的原则落到机制里。

## 一、为什么要追踪模型迭代

模型发布后不是一成不变的，创作者会：

- **修 bug**：修复输出异常、工具调用失败、特定输入崩溃等问题。
- **提质量**：用更好的数据或训练方法重训，能力提升。
- **换许可**：少数模型会调整许可证（放宽或收紧），直接影响能否继续商用。
- **补能力**：新增图像、推理、工具调用等特性。

不追踪的代价：一直用着旧权重，错过修复和提质；许可变更浑然不知，埋下合规雷。因此需要一套轻量的机制，定期比对"我本地记录的"和"仓库现在的"。

## 二、升级追踪机制：快照 vs 公开仓库

核心原理非常朴素——对比时间戳：

```
本地状态文件(快照)  ──记录──>  模型ID + 上次 lastModified + 许可
        │
        ▼
公开仓库 API 查询当前 lastModified
        │
        ▼
  当前 ≠ 快照  ──→  报告"有新迭代，建议评估"
  当前 = 快照  ──→  无变化
```

状态文件是一个本地 JSON（如 `watch.json`），形如：
`{"models": {"Qwen/Qwen3-7B-Instruct": {"last_modified": "2026-09-01T10:00:00Z", "license": "apache-2.0", "recorded_at": "2026-09-05T08:00:00Z"}}}`——即每个模型记录上次更新时间、许可、登记时间。

| 环节 | 做什么 | 命令 |
|---|---|---|
| 登记基线 | 首次记录某模型当前的更新时间 | `init --model X --state f.json` |
| 检查更新 | 对比当前仓库时间与基线，列出变化 | `check --state f.json` |
| 查看清单 | 列出正在追踪哪些模型 | `list --state f.json` |

注意：`check` 一旦检测到更新，会把快照里的基线**更新为新时间**（避免每次都重复报同一个更新），并把变化写进报告的 `updates` 列表。这个"只更新快照、不动本地模型"的设计，正是"只报告不自动升级"的落点。

## 三、配置定期轮询任务（每周一次）

追踪器是数据源，轮询任务负责"定期调用它并提醒你"。配置思路：

1. **状态文件路径**：放稳定位置（如 `~/.workbuddy/model-watch.json`），别用 `/tmp`（重启会丢）。
2. **登记模型**：每个模型跑一次 `init` 建立基线。
3. **创建周期任务**：用 cron / 自动化任务设一条**每周**执行的任务，动作是 `check --state <文件> --json`。
4. **提醒逻辑**：任务读输出的 `updates` 数组——非空就提醒人评估，为空则静默。
5. **提示词要点**：写明"只报告更新，不自动拉权重、不自动改配置，交给人决定"。

cron 示例（每周一 09:00）：`0 9 * * 1  cd <skill目录> && python3 scripts/upgrade_watch.py check --state ~/.workbuddy/model-watch.json --json`

`updates` 每条含 `old`/`new` 时间戳和 `suggestion`，可直接作为提醒内容。

## 四、升级评估清单：检测到更新后做什么

收到更新提醒**不等于立刻升级**。按清单逐项确认：

| # | 检查项 | 要确认什么 |
|---|---|---|
| 1 | 改了什么 | 看仓库 release notes / 提交记录：是修 bug、提质，还是仅仅文档改动 |
| 2 | 许可有无变化 | 对照新版本的 LICENSE；若从可商用变为受限，**停止升级并考虑替换** |
| 3 | 格式与端点兼容 | 新版是否仍提供 GGUF；Ollama 标签是否需要改；工具调用/识图能力是否变化 |
| 4 | 硬件是否还跑得动 | 新版体积是否变大，是否超出可用内存（见文档 01 硬件分档） |
| 5 | 是否值得重拉 | 改动很小或与你的场景无关，可跳过；改动实质相关才升 |
| 6 | 先备份 | 重拉前记录当前模型版本与配置；`models.json` 也先备份 |
| 7 | 回归验证 | 升级后跑几个典型任务，确认输出质量与工具调用没有退化 |

一句话：**更新是"建议"不是"命令"，逐项评估、确认有价值再动手。**

## 五、回滚预案

升级也可能翻车（新版变差、不兼容、许可变更）。提前准备回滚：

- **保留旧权重**：升级前记下当前 Ollama 标签；新版有问题就切回旧标签，验证通过前别删旧版本。
- **备份配置**：改 `models.json` 前 `cp ~/.workbuddy/models.json ~/.workbuddy/models.json.bak`，出问题直接还原。
- **保留基线记录**：状态文件保留历史更新时间，便于判断回退到哪个版本。
- **回滚触发条件**：质量明显下降、工具调用失效、许可变受限、内存不再够用——任一出现即回滚。
- **回滚后复核**：确认端点在线、任务正常，再把快照调整为旧版本基线（避免下次误报）。

## 六、只报告、不自动升级：为什么必须坚持

自动升级看似省事，风险却高：新版可能悄悄改许可（等于自动接受新条款，合规不可接受）；能力可能退化或与提示词不兼容，让线上效果突然变差；重拉权重也消耗流量与时间。

因此机制刻意设计成"检测→报告→人决定"：**脚本只动本地快照、只输出建议，绝不执行拉取、替换、改配置等动作。** 所有升级都是人在评估清单后主动做出的决定。

## 七、配套工具

升级追踪由 `scripts/upgrade_watch.py` 完成，只读公开 API、免费无 Key、状态存本地（部分网络环境不可达会明确报错）：

```bash
# 1. 登记要追踪的模型，建立基线
python3 upgrade_watch.py init --model Qwen/Qwen3-7B-Instruct --state ~/.workbuddy/model-watch.json

# 2. 检查是否有新版本（轮询任务定期调用这条）
python3 upgrade_watch.py check --state ~/.workbuddy/model-watch.json --json

# 3. 查看当前追踪清单
python3 upgrade_watch.py list --state ~/.workbuddy/model-watch.json
```

`check` 的 JSON 输出含 `updates`（变化的模型）、`errors`（查询失败的模型）、`note`（"本工具只报告更新，不自动升级；是否重拉权重由人决定"），可据 `updates` 是否为空驱动提醒。退出码 0=完成，1=参数或网络错误。网络失败时如实报告，不编造更新时间。
