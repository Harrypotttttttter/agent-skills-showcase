# 选型方法论

这份文档解决一个核心问题：面对几十个开源模型，如何用一套可复算的标准，挑出"在用户这台机器上、为这件具体的事"最合适的那一个，而不是盲目追榜单第一。

## 一、为什么"最合适 ≠ 榜单第一"

榜单（如各类 leaderboard）衡量的是模型在标准测试集上的综合能力，但它回答不了三个落地问题：

- **跑不跑得动**：一个 27B、17GB 的旗舰模型，在 8G 内存的机器上根本加载不了，能力再强也是零分。
- **对不对口**：一个推理冠军拿来做中文客服，可能不如一个中文特化、带识图的中等模型好用；榜单不测你的具体场景。
- **划不划算**：旗舰模型往往速度慢、占用高，日常问答用它属于"杀鸡用牛刀"，体验反而更差。

因此选型的目标不是"全局最强"，而是**在合规、硬件、诉求三重约束下的效用最高**。这是一个可以被拆解、被打分、被复算的工程判断，而不是凭感觉。

## 二、综合分模型：四个维度与权重

选型器把"合适程度"量化成一个 0-100 左右的综合分：

```
综合分 = 诉求匹配(40) + 硬件适配(25) + 榜单质量(20) + 大小速度平衡(15)
```

| 维度 | 权重 | 计算方式 | 为什么这样设权重 |
|---|---|---|---|
| 诉求匹配 | 40% | 场景命中=40 分，未命中=12 分；若明确要识图且模型支持，再加 3 分 | 用户要它干什么，是选型的出发点。选错场景，后面全无意义，所以权重最高 |
| 硬件适配 | 25% | 能跑且占用落在可用内存 30%-70% 甜点区=25 分；太富余或吃紧=约 21 分；跑不动直接淘汰 | "跑不动=零分"是硬约束，权重必须高；但只要能舒服跑起来，边际差异不大 |
| 榜单质量 | 20% | 质量档(1-5)/5 × 20 | 能力是基础盘，但不能唯榜单论——它只在合规与硬件都过关后才参与排名 |
| 大小速度平衡 | 15% | (速度×0.6 + 质量×0.4)/5 × 15 | 速度优先（对话场景体感明显），同时不让质量被牺牲太多；速度权重略高于质量 |

权重设计的内在逻辑：**先筛掉不能用的（许可、硬件是准入），再在能用的里面比谁最对口（诉求），最后用能力和体感做微调（质量、速度）**。

## 三、准入红线：只收免费可商用模型

在进入打分之前，先过一道硬性准入：

| 准入条件 | 说明 |
|---|---|
| 许可证白名单 | 只接受 Apache-2.0、MIT；两者都明确允许商用、修改、再发布，且几乎无附加义务 |
| 零付费 / 零 Key | 不收录任何需要付费、订阅、API Key 才能用的权重或端点 |
| 开源权重 | 必须能拿到权重本地运行，闭源 API 不进选型目录 |

BSD-2/3-Clause 在孵化审查里也视为可商用（见文档 03），但选型目录收敛到最常见的 Apache/MIT，减少判断分歧。**任何有 MAU 限制、禁止商用、或要求同源代码的许可，都不进推荐。**

## 四、7 个场景标签：含义与选什么

选型器用 7 个标签描述诉求。每个标签对应一类模型特性：

| 标签 | 诉求含义 | 应优先选的模型特性 | 目录中的代表 |
|---|---|---|---|
| `general` | 日常问答、通用助手 | 综合均衡、中文好、带识图加分 | Qwen3.5 9B / 27B |
| `coding` | 写代码、改 bug、看代码 | 代码能力强、推理好 | Qwen3.5 9B / 27B、Phi-4 14B |
| `reasoning` | 数学、逻辑、复杂推理 | 有思维链/强推理，参数不必最大 | DeepSeek-R1 Distill 8B、Phi-4 14B |
| `vision` | 识图、图文理解、多模态 | 必须支持图像输入 | Qwen3.5 9B、Gemma 4 E4B |
| `chinese` | 中文为主的任务 | 中文语料充分、中文评测高 | Qwen3.5 系列、GLM-4.7-Flash |
| `lightweight` | 端侧、低配、极速响应 | 体积小、速度快、能上小内存 | Qwen3.5 0.6B/4B、Gemma 4 E4B |
| `agent` | 工具调用、多步任务、智能体 | 工具调用稳、指令遵循好 | GLM-4.7-Flash 30B、Qwen3.5 27B |

实操提示：一个模型常同时命中多个标签（如 Qwen3.5 9B 命中 general/coding/vision/chinese/agent），这正是它"综合最均衡"的体现。场景命中越多，诉求分越稳。

## 五、硬件分档表：你的机器能跑什么

选型器用一条经验规则估算可分配给模型的内存：

```
可用内存 ≈ 物理内存 × (Mac 统一内存 0.70 / 普通机器 0.60)
```

模型体积（Q4 量化后）必须小于可用内存，否则淘汰；占用落在可用内存的 30%-70% 是体验甜点区。

| 物理内存 | 可用(约) | 能舒服跑的模型规模 | 参考体积 | 速度体感 |
|---|---|---|---|---|
| 8G | Mac 5.6G / 普通 4.8G | 0.6B - 4B | 0.5-3.2GB | 4B 约 15-25 tok/s，0.6B 极快 |
| 16G | Mac 11.2G / 普通 9.6G | 4B - 14B | 3.2-8.5GB | 9B 约 8-15 tok/s，流畅 |
| 24G | Mac 16.8G / 普通 14.4G | 9B - 27B | 6.6-17GB | 27B 约 3-6 tok/s，偏慢但可用 |
| 32G+ | Mac 22.4G+ / 普通 19.2G+ | 27B - 35B(MoE) | 17-24GB | 27B 约 5-8 tok/s；MoE 模型更快 |

说明：速度数字是 CPU/普通 GPU 上的大致量级，受硬件差异影响很大，仅作相对参考。MoE 模型（如 35B-A3B）虽然标称参数大，但每步只激活一小部分（3B），对内存要求高、对算力要求低，32G 内存机器跑起来反而比同体积稠密模型快。

## 六、选型实战流程

按这个顺序走，避免反复试错：

1. **先问诉求**：用户拿模型干什么？落在哪个场景标签？有没有硬性要求（如必须识图）？
2. **确认硬件**：物理内存多少？是不是 Mac 统一内存？据此估算可用内存。
3. **跑选型器**：把诉求和硬件喂给脚本，拿到综合分最高的推荐和它的分项得分。
4. **看理由与备选**：读 `why` 字段理解分数怎么来的；同时看 2-3 个备选，必要时让用户二选一（如"更快的小模型" vs "更准的大模型"）。
5. **合规确认**：口头说明许可证、免费可商用、数据不出本机。
6. **收尾追问**：选完后主动问一句"要不要建个定期任务，盯这些模型有没有出新版？"

**汇报推荐时必带理由**：不要只说"选 A"，要说清诉求/硬件/榜单/速度各占多少，以及为什么没选榜单第一（通常是"那个跑不动"或"它更对口"）。

## 七、配套工具

选型由 `scripts/select_model.py` 完成，纯本地计算、零联网、零依赖：

```bash
# 查全部模型目录
python3 select_model.py --list

# 按场景 + 硬件选型
python3 select_model.py --scene general --ram 24 --mac

# 明确要识图，输出 JSON（便于程序解析）
python3 select_model.py --scene coding --ram 16 --need-vision --json

# 低配极速场景
python3 select_model.py --scene lightweight --ram 8 --json
```

关键参数：`--scene`（7 个场景标签之一）、`--ram`（物理内存 GB）、`--mac`（Mac 统一内存）、`--need-vision`（要求图像能力）、`--json`（结构化输出）、`--list`（列目录）。退出码 0=给出推荐，1=参数错误或无匹配模型。输出里的 `score_breakdown` 就是四个维度的分项得分，可直接用于向用户解释理由。
